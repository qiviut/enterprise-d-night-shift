# ADR-001: A living ship, deterministic rules, constrained AI

- **Status:** Accepted for the first delivery path
- **Date:** 2026-10-16
- **Owner:** Project integration lane

## Outcome

Build a first-person browser adventure set inside the USS Enterprise-D. Players walk or run through ship interiors and can open text chat at any time with the ship computer or a crew NPC. Hermes may create fresh dialogue and propose bounded mission events while a save is being played. The game server—not the model—owns movement, access, mission truth, rewards, persistence, and consequences.

This is a public fan project. Use original, procedurally assembled art and independently written presentation. Do not include extracted models, screenshots, music, logos, fonts, or other unlicensed franchise assets. A disclaimer does not grant distribution rights.

## Deliberate scope ladder

Keep the destination ambitious, but do not build it all at once.

1. **Skeleton:** one small greybox corridor/room route, smooth walk/run, collision, one interactable console, an always-available chat panel, and a deterministic offline reply. CI and tests work before visual expansion.
2. **First vertical slice:** a short EPS-disturbance incident with a ship-computer exchange, one crew NPC, evidence gathering, one meaningful choice, visible consequence, and save/reload.
3. **Hermes-backed slice:** isolated narrative worker, validated dialogue/event envelope, real integration test, and authored fallback when inference is unavailable.
4. **Ship expansion:** bridge, engineering, sickbay, Ten Forward, turbolift, scheduled crew, and follow-up missions added as separate accepted beads.
5. **Polish and deployment:** current-iOS device QA, performance work, tailnet service, backups, and operator-run installation.

The eventual content target is 10–12 explorable spaces, four or more conversational crew, and multiple incident families with more than one valid solution. That is not the first milestone.

## Stack and runtime boundaries

- **Client:** Vite + TypeScript + React for DOM/HUD/chat; Babylon.js for the 3D scene. Keep the render/input loop outside React state updates.
- **Rendering:** probe WebGPU before constructing the scene; use WebGL when WebGPU is unavailable or fails initialization. Babylon does not turn an existing WebGPU scene into WebGL, so select the backend before creating GPU resources. Use capability detection, not user-agent strings.
- **WASM:** not a requirement for the skeleton. Start with simple, deterministic TypeScript corridor collision and movement. Add a WASM physics/runtime dependency only if a benchmark on target phones demonstrates a material benefit.
- **Server:** Node.js + Fastify; share typed command/event contracts and deterministic rules with tests. SQLite/WAL is adequate for the single-host first release. Keep player saves isolated with unguessable server-issued session tokens; no account system is required for the initial tailnet deployment.
- **Transport:** HTTP for bootstrap, save/load, and chat submission; WebSocket for sequenced movement and authoritative events when the networked movement slice is introduced. The server validates all commands and rechecks prerequisites before effects.
- **Assets:** original modular interior kit, baked/static lighting where practical, compressed textures, instanced repeated details, and zone-based loading. The initial route must be playable before the asset kit expands.

### Browser target

As of 2026-10-16, Apple's security-release page lists iOS 27.0.1 as the latest iOS version (released 2026-09-28). WebKit shipped WebGPU in Safari 26.0 for iOS and other Apple platforms. Treat the newest iOS Safari as a tested target, not as a reason to remove the WebGL fallback. Test on an actual iPhone; simulator/browser emulation alone does not satisfy this gate.

- Prefer landscape, but do not require orientation-lock or fullscreen permission. In portrait, show a clear rotate hint and keep the chat accessible.
- Use a left-thumb movement stick, right-thumb look drag, run toggle, contextual interact, and persistent chat control. Cancel movement on pointer cancellation, blur, or opening the chat.
- Respect safe-area insets and the iOS software keyboard; pause hazard clocks while the player is typing.
- Keep text readable and targets comfortably touch-sized; reduce effects/resolution before reducing UI legibility.

## Game loop

The first story is “Night Watch”: a shipboard EPS disturbance interrupts the player's shift. The player checks a local console, asks the computer or crew for context, inspects a second signal, and chooses between two competing priorities. The server commits the choice and changes a visible ship condition; a later conversation or assignment reflects that outcome.

Running has no stamina grind. Progression unlocks access, diagnostic abilities, crew trust, and new incident combinations rather than arbitrary stat inflation. Chat with the ship computer is available anywhere; NPC chat is available in proximity or over an explicitly opened comm link.

## Hermes boundary

The browser never calls Hermes directly and never receives an `API_SERVER_KEY`. The game server calls a dedicated game-only Hermes profile through a `NarrativeBroker` interface. The profile must have an **empty effective tool registry**; the standard `hermes-api-server` preset is not sufficient because it still includes host-capable tools such as terminal and file access. Bind that profile to a separate API key and loopback endpoint. At startup, verify its effective tool set and fail closed to offline authored content if any tool is enabled. Do not point player traffic at the operator's normal Hermes profile.

The game sends only bounded, save-scoped context: current location, allowed world facts, relevant incident state, and a short recent dialogue window. Hermes returns a typed narrative envelope: plain-text reply plus optional references to shipped event templates. Server code validates the schema, maximum lengths, active save, state version, target allowlist, prerequisites, costs, cooldowns, and solvability before committing an event. Invalid, stale, duplicate, or unparseable output is rejected and replaced with authored fallback dialogue.

Treat player text and generated output as untrusted data. They cannot supply scripts, SQL, HTML, arbitrary URLs, asset paths, tools, or direct state patches. Do not give the narrative worker terminal, filesystem, browser, MCP, delegation, skill-install, or operator-memory access. Keep inference credentials outside the game process where possible and behind a fixed-route broker. Runtime evolution changes content/state only; it never changes deployed code.

Limit one active narrative job per save, response size, concurrency, cost, and deadline. A provider timeout, rate limit, worker crash, or unsafe tool configuration must not block movement or the mission: use authored dialogue and deterministic incident rules instead.

## Performance targets (not measurements)

These are acceptance targets to measure on named reference devices, not current results:

- 30 FPS minimum with p95 frame time at or below 34 ms; 60 FPS is a stretch target.
- Initial compressed client payload at or below 8 MiB.
- Interactive within 6 seconds on a 20 Mbps / 100 ms RTT test link.
- Run a 10-minute session with repeated room/zone transitions and check thermal behavior, memory, frame pacing, and input latency.

## Verification gates

- Unit/property tests for movement, collision, access checks, solvability, idempotency, reward-once behavior, save/reload, and stale narrative proposals.
- Contract tests for browser/server and server/NarrativeBroker schemas.
- Adversarial tests for prompt injection, malformed model output, forged client commands, cross-save access, oversized replies, and HTML/URL/script payloads.
- Fault tests for inference timeout/429, worker exit, reconnect, duplicate submission, interrupted write, and restore from backup.
- Browser E2E for the vertical slice and visual regressions at desktop, narrow portrait, and landscape viewports.
- Real-iPhone Safari acceptance for multitouch, keyboard, rotation, WebGPU and WebGL paths, context loss, thermal stability, and the current iOS release.
- Complete the same incident with Hermes disabled; the game remains playable.
- Tailnet deployment is accepted only after Tailscale is authenticated, the service binds locally behind Tailscale Serve, and the live health/save/chat paths are read back. CI never receives host deployment credentials.
